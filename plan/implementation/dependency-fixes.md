# Dependency fixes

This file records every change made to the "Depends on" and "Milestone" columns of the six epic files, and every interface task added, to turn the task graph into a buildable DAG. `dependencies.md` holds the generated checks; this file explains why each edge or milestone changed.

Rules, as cited in the "Rule applied" column:

- **R1 provider/consumer.** For a mutual pair across areas, the consumer depends on the provider and the provider's edge to the consumer is dropped. The provider is the task whose RFC defines the interface. When both sides genuinely need each other, an interface task (types, trait or format with stub tests) is added in the provider's epic at the earlier milestone and both depend on it.
- **R2 within-area cycle.** The same rule applied inside one area.
- **R3a re-point.** A dependency on a later milestone is re-pointed to an earlier task that delivers enough (an interface, stub or first-backend task).
- **R3b split.** The dependent is split into a core task at its own milestone and an extension task at the later one.
- **R3c move.** The dependent moves to the later milestone; its own dependents were checked.
- **R4 M0 closure.** An M0 task may depend only on M0 tasks.
- **R5 split milestone.** A task whose milestone is written as a range was checked against its dependency's range.
- **R6 M0a closure.** An M0a task may depend only on M0a tasks. The walking skeleton's seed tasks and their full dependency closure are M0a; every other M0 task is M0b.
- **R7 platform split.** A plain M1 task is M1b when it is Windows, macOS, Metal or Apple work; every other M1 task is M1a. A cross-platform M1a task that depended on such work loses that edge. A new M1b extension task, "Windows and macOS part of <ID>", depends on it and on the platform tasks, and carries its criteria on the Windows and macOS rigs.
- **R8 false edge.** An edge whose prerequisite the dependent's acceptance criteria do not use is cut, or re-pointed to the smaller task that delivers what they use.
- **R9 criteria closure.** A task depends on every task that produces something its acceptance criteria use. When that producer is in a later milestone, the criterion moves to a task in that milestone: an existing task that covers it, or a new one.
- **Word resolution.** A dependency written in words was rewritten as explicit task IDs (descriptive text kept in parentheses), or resolved with an entry in `map-overrides.tsv`.

Read "A → B" as "A depends on B".
