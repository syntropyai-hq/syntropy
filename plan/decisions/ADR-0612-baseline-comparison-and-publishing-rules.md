# ADR-0612: Baseline comparisons under identical conditions, and commit-tied publishing
- Status: Accepted (2026-10-20)
- Date: 2026-10-19
- Deciders: maintainers (drafted in the quality and release engineering area)
- Related: ADR-0000 (D3, D5), ADR-0004, ADR-0019, ADR-0610; RFC-0060; RFC-0061 §7, §11

## Context
Syntropy's value claim is comparative: the largest model at the highest tokens/s the hardware can deliver, which implies faster than what a user could otherwise run. The survey shows how such claims go wrong:
- headlines ahead of code;
- "4× faster" over a table showing 2.8×;
- benchmark bars whose quantization could not fit the stated machine;
- numbers that went 4–5× stale within weeks;
- defaults quietly approximate while the headline claims exactness

(`multi-device-inference.md` §13 item 17; `tiered-memory-inference.md` §17, §18). D3 makes exactness the default, so a speed comparison that ignores fidelity is misleading. D5 forbids naming third-party inference systems in plan documents.

## Options considered
1. **Compare against published numbers from other projects.** No effort, but the conditions are unknown and unreproducible.
2. **Compare against one fixed, named reference engine.** Simple, but naming it in plan documents violates D5, and a fixed choice goes stale as the field moves.
3. **No comparisons, only absolute numbers and efficiency against the hardware bound.** Honest, but it leaves users unable to judge whether switching is worth it.
4. **Chosen: compare against the best available baseline per (rig, model class), chosen by a documented selection run.** It runs under identical conditions, interleaved, tuned in the baseline's favour, with both engines' fidelity reported. Every published number is generated from the results store and tied to a commit and a raw-data bundle.

## Decision
1. **Selection.** Per (rig, model class), the baseline is the fastest publicly released engine that runs the same model bytes on that rig, or bytes per token within 2% (labelled `format-adjusted`). A selection run is made per release cycle and on candidates' releases. Selection results are kept.
2. **Identical conditions.**
   - The same rig, image and epoch, and the same thermal protocol.
   - The same token IDs, or the same token count ±1 when only text input is possible.
   - Greedy decoding with EOS ignored, and prefix caching off unless the scenario is about caching.
   - ABBA blocks with cold restarts.
   - Load time is timed separately from steady-state metrics.
3. **Asymmetric tuning, in the baseline's favour.** The baseline uses its documented recommended configuration plus a sweep of up to 20 documented performance options. Syntropy runs its defaults.
4. **Fidelity on both sides.**
   - Syntropy runs exact, with its parity report attached.
   - The baseline runs twice, `baseline-default` (with its approximations listed) and `baseline-exact`, and is measured with the RFC-0060 corpus wherever it exposes top-n log-probs.
   - The headline is exact against exact.
5. **Multi-device comparisons** are made against a baseline only on the same topology. Otherwise they are labelled "Syntropy on this cluster against the best baseline on the best single machine of it".
6. **Publishing.**
   - No hand-typed numbers. Every figure carries its full key (commit, rig, model and quant, lengths, concurrency, interconnect, thermal protocol, fidelity, date) and the hash of a downloadable raw-data bundle with exact reproduction commands.
   - Numbers are labelled measured, estimate or target.
   - Nothing is extrapolated.
   - Numbers go stale automatically after two releases or a rig epoch change.
   - A placeholder performance value in docs blocks the release.
   - No capability claim is made without a passing suite in the same release.
   - Corrections are dated errata.
   - User-run results stay with users unless contributed with consent, and are labelled community-reported.
7. **Naming** (revised 2026-10-20). Plan documents never name baseline engines (D5), and this ADR is written without them. Benchmark records and raw-data bundles name them, so results can be reproduced. Public benchmark reports name the baseline too, under every one of these conditions:
   - the name comes with the exact version and the configuration used;
   - no logos or trade dress;
   - a line saying that names belong to their owners and imply no endorsement;
   - only figures generated by this ADR's pipeline, with the raw-data bundle attached;
   - factual wording, with no disparaging adjectives;
   - the baseline's maintainers are invited to check the configuration 14 days before the first publication that names a new baseline. Corrections after that are dated errata (decision 6).

   - **When numbers go public.** Syntropy-only nightly numbers are public from M2, when the results site exists. Nightly *comparisons* against baselines stay private until M4, when the release gate is calibrated and enforced. Release comparisons follow the same conditions from the first release that publishes one.
8. **The M1a-exit thesis checkpoint** (added 2026-10-20; a pilot of OQ-PRC-03). Every SC row measures Syntropy against the hardware bound or its own model, so nothing else tests the value claim: that Syntropy beats what the same user could already run on the same machine. A single-device comparison on R-ADA under decisions 1–4, on scenarios (a) and (b2), in the release design (ABBA × 4 with k = 3), with the headline exact against exact.
   - **Early read (S-10).** At the M0b exit, a throwaway harness runs the same comparison on dense in-VRAM decode, to see whether executor overhead rather than the kernels is the gap. It informs; it does not gate.
   - **The condition.** The checkpoint passes when Syntropy's decode rate is ahead of the selected baseline's on scenario (a) or (b2), with the sign-flip test's p < 0.05 in Syntropy's favour (RFC-0061 §3.4). It is an M1a exit criterion: if it fails, M2's scope is re-planned before M2 work starts.
   - **Release gate.** From the first M1a RC, `rc-gate` runs the same comparison on the RC's artefacts and fails when the checkpoint condition does not hold, unless a maintainer waives it in writing with the measurement attached. The waiver is copied into the release notes.
   - **Scope growth.** Rig (c), the S2 cluster, joins at M2 under decision 5's labelling.

## Consequences
- **Positive.**
  - Comparisons are reproducible by anyone with the same hardware.
  - Tuning asymmetry makes a Syntropy win robust.
  - Fidelity reporting stops "fast because approximate" from passing as a win.
  - Stale or unsupported claims are removed by tooling, not by memory.
- **Negative.**
  - Selection runs and baseline sweeps cost lab time each release cycle.
  - Some baselines cannot load the same files or expose log-probs, so their comparisons carry labels and caveats.
  - Naming baselines needs a 14-day invitation to the baseline's maintainers before each new baseline's first publication.
  - The thesis checkpoint costs R-ADA time at the M1a exit and on every RC, and a failed checkpoint re-plans M2.

## What would make us revisit
- A baseline's maintainers dispute a published configuration and the dispute is upheld. Then correct it by dated erratum, and extend the invitation period for that baseline.
- Comparative-advertising rules where a report is published turn out to forbid one of the conditions' practices. Then publish by role until the template is fixed. Plan documents stay bound by D5 either way.
- Baseline sweeps exceed 25% of a rig's RC budget. Then cap them to the options that moved the result in the previous cycle.
- A baseline's license or terms forbid benchmarking or publishing results. Then drop it from selection and record why.

## Revisions
- Revised 2026-10-20: decision 7 names baselines in public reports under six conditions, because describing a baseline by role while its name sits in the downloadable bundle shelters nothing and makes the report harder to verify; Syntropy-only nightly numbers are public from M2 and nightly comparisons wait for M4's calibrated gates. Decision 8 adds the M1a-exit thesis checkpoint, with an M0b-exit early read, as an M1a exit criterion and a release gate from the first M1a RC. RFC-0061 Open questions 2 and 9 are answered by decision 7.
