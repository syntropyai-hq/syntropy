24 GB のグラフィックスカードと 64 GB の RAM を積んだゲーミング PC、48 GB のユニファイドメモリを持つノート PC、テレビの下にある 128 GB のミニ PC。どれも単体では、4 ビットで 142 GB になる 2,350 億パラメーターの Mixture-of-Experts（MoE）モデルを載せられません。しかし 3 台を合わせれば 264 GB あります。

Syntropy はこれらを、複数種類のメモリを持つ 1 台のコンピューターとして扱います。各 GPU と CPU が各メモリ階層をどれだけ速く読み出せるかを測り、モデル全体に対して 1 つの配置を選び、計算をデータのそばで行います。つまり、ある重みを自分のメモリに保持しているデバイスが、その重みを使う計算も担当します。デコード中にマシン間を流れるのはアクティベーションだけです。マシン内では、GPU のキャッシュにない重みを、トークンごとに PCIe 経由でコピーするのではなく、その重みが置かれている場所で CPU が計算します。

## 機能

以下はすべて設計で仕様が定められているもので、まだ何も実装されていません。

### 1 台のマシンの中で

- **すべてのメモリ階層が仕事をする**。最もホットな重みと MoE のエキスパートは、適応型の VRAM キャッシュに置かれます。重み全体は RAM に常駐し、キャッシュミスは CPU がその場で計算します。コールドなエキスパートや大きなテーブルは、必要になったときに NVMe からダイレクト I/O で読み出します。
- **エキスパートは必要になる前に取得する**。次の層のエキスパートの予測はルーターカーネルの中で実行されます。そのため、現在の層を計算している間に、次の層のための NVMe と RAM からの読み出しが進みます。
- **カタログ値ではなく実測値**。各マシンは Syntropy の実際のカーネルを使い、GPU、CPU、ドライブ、ネットワークリンクが実際に出せる性能を計測します。配置はスペックシートではなく、その計測結果から組み立てます。

### 複数のマシンにまたがって

- **モデル全体で 1 つの配置**。1 つのプランが、どのマシンが参加するか、各マシンがどの層範囲を実行するか、各テンソルグループをどの階層に置き、どのデバイスで計算するかを決めます。各グループがなぜその場所に置かれたのかも記録します。
- **マシンのリング**。モデルはパイプラインステージに分かれ、各ステージは隠れ状態を次のマシンへ直接渡します。1 つの層を複数のマシンに分割するのは、Thunderbolt 5 上の RDMA のように、実測レイテンシが判定基準を満たすリンクの場合に限ります。
- **LAN では設定不要、LAN の外ではトークン 1 つ**。同じネットワーク上のマシンは互いを検出します。新しいマシンは、両方の画面に同じ 6 桁のコードが表示されていることを確認すると参加が承認されます。外出先のノート PC は、デフォルトで 1 回限り有効な招待トークンで参加します。
- **マシンが抜けても回答は失われない**。各ステージは直近に送信した内容を保持します。あるステージのマシンが離脱しても、残りのマシンに余裕があれば、クライアントにエラーを返すことなく生成が再開されます。

### ユーザーとツールのために

- **指定しない限り厳密**。キャッシュミスしたエキスパートの計算を省くなど、出力を変えるショートカットはオプトインです。それぞれに名前があり、影響したすべてのレスポンスに明記されます。
- **回答を変えない投機的デコーディング**。MTP ヘッドまたはドラフトモデルが複数のトークンを提案し、モデルがそれらを 1 回のパスでまとめて検証します。受理ルールにより、モデル本来の出力分布は保たれます。
- **ツールが既に使っている API**。OpenAI 形式と Anthropic 形式の API、そしてネイティブ API を、リクエストが届いたどのマシンからでも提供します。
- **全体がネイティブコード**。Rust で書かれたシステム層、CUDA、HIP、Metal、Vulkan、CPU 向けのネイティブカーネル、そして対応範囲を広げるための演算単位のフォールバックとしての ggml。

## 使い方のイメージ

以下は [RFC-0051](plan/rfcs/RFC-0051-cli-and-dashboard.md) で計画されているコマンドラインです。これらのコマンドはまだどれも存在しません。

```sh
syntropy run                     # 質問を 1 つしたあと、載せられるモデルを推奨する
syntropy plan <model> --explain  # ロードせずに配置と予測速度をプレビューする
syntropy cluster approve <id>    # 6 桁のコードを照合して、LAN 上のマシンの参加を承認する
syntropy invite create           # 外出先のノート PC 用の 1 回限りのトークン
```

各マシンはデフォルトで `http://127.0.0.1:7433` で API を提供するため、既存の OpenAI や Anthropic のクライアントと SDK がそのまま使えます（[RFC-0050](plan/rfcs/RFC-0050-api-surface.md)）。

```sh
curl http://127.0.0.1:7433/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model": "<model>", "stream": true,
       "messages": [{"role": "user", "content": "なぜデコードはメモリ律速なのですか？"}]}'
```

## 仕組み

1 人のユーザーに 1 トークンを生成するたびに、アクティブな重みすべてと KV キャッシュ全体を 1 回ずつ読み出します。1 バイトあたりの演算量は小さいので、デコード速度は、データがどこにあり、そのそばのプロセッサーがどれだけ速く読み出せるかで決まります。Syntropy はこの性質を前提に設計されています。計算をデータのある場所へ移し、データの配置は実測に基づいて決めます。

### 1 台のマシンの中で

<p align="center"><img src="docs/media/tiers.svg" width="760" alt="1 台のマシン：VRAM はホットな重みとエキスパートキャッシュを保持し、GPU が読み出す。RAM はすべての重みを保持し、キャッシュミスは CPU がそこで計算する。NVMe はコールドなエキスパートとテーブルを保持し、RAM へプリフェッチされる"></p>

- **VRAM** には、すべてのトークンが触れるもの（アテンション、dense 層、共有エキスパート、KV キャッシュ）と、最もよく使われる MoE エキスパートのキャッシュを置きます。このキャッシュはワークロードに合わせて変化します。
- **RAM** には重み全体を置きます。トークンが GPU のキャッシュにないエキスパートを必要とするときは、PCIe 経由でコピーする代わりに、CPU が GPU と並行して RAM 上で計算します。デスクトップ CPU はデュアルチャネル DDR5 を 76〜122 GB/s で読み出せます。これは PCIe 4.0 x16 が GPU に届ける帯域の約 3〜5 倍です。
- **NVMe** には、コールドなエキスパートと大きなルックアップテーブルを、エキスパート単位のエクステントとして格納し、ダイレクト I/O で読み出します。次の層の予測によって、ルーターが要求する前にその読み出しが始まります。

Syntropy の階層マネージャーがメモリに常駐するすべてのバイトを管理するため、何をメモリに残すかを OS のページキャッシュが決めることはありません。重みを GPU へストリーミングするのは、長いプロンプトのチャンクのような大きなバッチの場合だけです。それも、実測した損益分岐点から、その場で計算するよりコピーするほうが有利と判断できる場合に限ります。

### 複数のマシンにまたがって

<p align="center"><img src="docs/media/ring.svg" width="760" alt="リング状につながった 3 台のマシン。それぞれが 1 つの層範囲を実行する。隠れ状態は次のマシンへ順に渡され、最後のマシンがトークンをサンプリングして最初のマシンに戻し、リクエストを受け取ったマシンへストリーミングする"></p>

モデルは層範囲ごとにステージに分けられ、1 台のマシンが 1 つのステージを担当し、ステージ同士でリングを構成します。最初のステージが入力を埋め込みベクトルに変換し、各ステージは自身の隠れ状態を次のステージへ直接渡します。最後のステージがトークンをサンプリングし、リングを回して先頭に戻すとともに、リクエストを受け取ったマシンへストリーミングします。パイプラインが増やすのは単一ストリームの速度ではなく容量です。そのため、速度の向上はデータをより高速なメモリに移すことから生まれます。ホップを 1 つ増やすだけになる低速なマシンは、リングから外します。

テンソル並列やエキスパート並列で 1 つの層を複数のマシンに分割すると、トークンごと・層ごとにネットワークの往復が 1 回発生します。Syntropy がこれを行うのは、実測した集団通信のレイテンシが十分に低く、元が取れるリンクだけです。実際には RDMA クラスのリンクがこれにあたります。Wi-Fi が条件を満たすことはありません。

1 台のマシンがコーディネーターに選出され、メンバーシップとプランを記録するクラスターのイベントログを管理します。コーディネーターはトークンを一切扱わず、リクエストパス上にもないため、失われてもリクエストが失敗することはありません。

> [!TIP]
> より詳しく平易な解説は [docs/HOW_IT_WORKS.md](docs/HOW_IT_WORKS.md) にあります。詳細な設計は各 RFC にまとめています。階層と常駐（[RFC-0020](plan/rfcs/RFC-0020-tier-manager-and-residency.md)）、重みの I/O パス（[RFC-0021](plan/rfcs/RFC-0021-weight-io-path.md)）、エキスパートキャッシュ（[RFC-0023](plan/rfcs/RFC-0023-moe-expert-cache-prediction-prefetch.md)）、配置（[RFC-0011](plan/rfcs/RFC-0011-joint-placement-solver.md)）、分散実行（[RFC-0032](plan/rfcs/RFC-0032-distributed-execution.md)）、ディスカバリーと招待（[RFC-0030](plan/rfcs/RFC-0030-discovery-membership-invites.md)）です。

## デフォルトで厳密

デフォルト設定では、Syntropy の出力は、同じモデルを同じ量子化で実行したリファレンスのフォワードパスと、公開された許容誤差の範囲内で一致しなければなりません（[ADR-0019](plan/decisions/ADR-0019-exactness-contract.md)）。

- **リファレンス**は Syntropy のリファレンス実行器です。F32 での累積、固定されたリダクション順序、同じファイルから厳密に逆量子化した重みを使います。このリファレンス自体もモデル公開元のリファレンス実装と照合されるため、「厳密」はカーネルだけでなく、Syntropy によるモデルの解釈にも及びます。
- **テスト**は、チャット、コード、長いコンテキスト、ツール呼び出しの JSON、多言語テキストからなるバージョン管理されたコーパスに対する、teacher forcing での top-1 一致率と KL ダイバージェンスです。許容誤差は dtype クラスごとに計測に基づいて定め、バージョン管理し、すべてのリリースに記録します。
- **合格が必要なもの**は、厳密モードでプランナーが選びうるすべての経路です。各カーネルとフォールバック、GPU 1 基からマシンのリングまでの各配置形態、投機的デコーディングと通常のデコーディング、階層間の KV ページング、再開したセッション。不合格の経路は、本来の意図にかかわらず近似として扱います。
- **ショートカットはオプトインで、名前が付いています**。たとえば `expert_skip`（キャッシュミスしたエキスパートを計算しない）や `kv_lossy`（KV をモデルの精度より低い精度で保存する）です。すべてのレスポンスに、その忠実度と有効だったショートカットが明記されます。`exact` を要求したリクエストに、近似の構成で応答することはありません。

異なるデバイス間で、バイト単位まで同一の出力は保証しません。ハードウェアによって、許容誤差の範囲内で丸め方が異なるためです。同じビルドと同じデバイスで再現可能な出力を得るための、より低速な `deterministic` モードを計画しています。許容誤差とパリティハーネスは [RFC-0042](plan/rfcs/RFC-0042-quantization-and-numerical-fidelity.md) と [RFC-0060](plan/rfcs/RFC-0060-testing-and-correctness.md) で規定しています。

## コントリビューション

Syntropy は、AI エージェントがプランのタスクを実行することで構築されます。エージェントはタスクを 1 つ引き受けて専用のブランチで実装し、タスクの受け入れ基準を満たし、実装する RFC のセクションと ADR を明記した変更を 1 つ提出します。どのタスクに着手できるかはタスクグラフが決めます。

変更がマージされるのは、次のすべてに合格した場合だけです（[ADR-0021](plan/decisions/ADR-0021-development-model-ai-agents-open-source.md)）。

- ビルド、lint、フォーマット、そしてユニットテスト、プロパティテスト、シミュレーターテスト
- パリティハーネスと適合性ゲート
- 変更が計測対象の経路に触れる場合は、性能回帰ゲート
- 依存関係とライセンスのポリシー、命名チェック、タスクグラフチェック
- 独立したレビューエージェントによる承認。変更を書いたエージェントとは必ず別のエージェントが、タスクの受け入れ基準と引用された RFC のセクションに照らして変更を検査します。

パリティハーネスと適合性ゲートは、それらが検査するカーネルやモデルファミリーより先に、M0 で最初に構築します。慎重を要する種類の変更は、メンテナーの承認も必要です。対象は、鍵、署名、参加承認、アップデートクライアント、CI とリリースの設定、エージェント向けの指示ファイル、新しいモデルファミリー、新しい直接依存、そしてゲートで検査できない変更やゲートの免除が必要な変更です。

外部からのコントリビューションも、同じゲートのもとで歓迎します。[CONTRIBUTING.md](CONTRIBUTING.md) では Issue、プルリクエスト、エビデンス、AI を活用した作業について説明しています。[AGENTS.md](AGENTS.md) はエージェント向けの作業ガイドです。

## セキュリティ

脆弱性は公開の Issue ではなく、非公開で報告してください。[SECURITY.md](SECURITY.md) に、報告の窓口、対応目標、そして Syntropy がネットワークに公開する予定の機能（LAN ディスカバリー、ペアリング、招待リンク、API、アップデートチャネル）の概要があります。

## ライセンスとクレジット

Syntropy は、[MIT](LICENSE-MIT) と [Apache-2.0](LICENSE-APACHE) のどちらかを選んで利用できるライセンスで提供されます。コントリビューションも同じ条件で受け付け、すべてのコミットに Developer Certificate of Origin の sign-off が必要です（[ADR-0018](plan/decisions/ADR-0018-licence.md)）。

Syntropy のカーネル層は、MIT ライセンスのテンソルライブラリである [ggml](https://github.com/ggml-org/ggml) を基盤とします。ggml は幅広いバックエンドへの対応と、ネイティブカーネルを持たないすべての演算のフォールバックを提供します。各リリースには、含まれるすべてのコンポーネントを列挙した自動生成の `THIRD-PARTY-NOTICES` ファイルを同梱する予定です。Syntropy はモデルの重みを配布しません。各モデルにはそれぞれ独自のライセンスが適用されます。
